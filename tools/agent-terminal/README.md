## 一、产品概述（纠正版）

### 1.1 这是什么 — 重新定义

Agent Terminal 是一个运行在代理商本地的 **凭证采集工作站**。

它的核心职责是：

> **通过各种自动化/半自动化手段，从第三方平台获取支付凭证（支付链接、二维码、卡密等），预存到 Super Market 平台的库存池中。**

### 1.2 关键业务流程纠正

```
❌ 之前错误的设计：
   第三方平台 → 工具生成凭证 → 上传平台 → API下单 → 工具交付

✅ 正确的业务逻辑：
   
   ┌─────────────────────────────────────────────────────────┐
   │                     Agent Terminal                      │
   │                                                         │
   │  浏览器自动化  ──→  扫码登陆第三方平台                  │
   │  模拟器抓包   ──→  进入支付页面/App                      │
   │  Cookie复用   ──→  捕获支付链接/二维码/卡密              │
   │  手动录入     ──→  上传到 Super Market 平台              │
   │                                                         │
   │                    ▼                                    │
   │              平台库存池（预存）                          │
   │              代理商积分被扣除作为担保                     │
   └──────────────────────┬──────────────────────────────────┘
                          │
                          ▼
   ┌─────────────────────────────────────────────────────────┐
   │              API 支付商发起订单                          │
   │                                                         │
   │  检查库存池 → 有资源 → 订单创建成功 → 消耗资源          │
   │               → 无资源 → 订单创建失败                    │
   │                                                         │
   │  整个过程中，工具只需要做一件事：                        │
   │  持续不断地往库存池里"喂"凭证。                          │
   └─────────────────────────────────────────────────────────┘
```

### 1.3 核心价值（重新定义）

| 痛点 | 解决方案 | 价值 |
|------|---------|------|
| 手动去各个平台复制支付链接，效率极低 | 浏览器自动化 + 模拟器抓包，一键批量采集 | 效率提升 50x+ |
| 多平台账号管理混乱，Cookie 频繁过期 | 统一账号管理 + 自动续期 + 异常提醒 | 减少人工维护成本 |
| 支付链接有时效性，过期了不知道 | 自动检测过期 + 自动补货策略 | 保障库存池健康度 |
| 部分平台有反爬/验证码/设备指纹 | 多种采集手段组合（模拟器/浏览器/App抓包） | 覆盖几乎所有平台 |

### 1.4 产品一句话定位

> **一个"凭证猎人"——用尽一切手段从第三方平台获取支付凭证，喂给 Super Market 的库存池。**

## 二、凭证采集手段全景（核心设计）

这是工具最核心的部分。针对不同的第三方平台和安全防护等级，设计多种采集手段。

### 2.1 采集手段总览

```
采集手段
│
├── A. 浏览器自动化（PC 端）
│   ├── A1. 全自动模式（Cookie 有效）
│   ├── A2. 半自动模式（需人工扫码/验证码）
│   └── A3. 手动辅助模式（标记页面元素）
│
├── B. Android 模拟器抓包（App 端）
│   ├── B1. 自动代理抓包（mitmproxy / Charles）
│   ├── B2. App 内嵌 WebView 注入
│   └── B3. ADB 命令自动化
│
├── C. 网络请求捕获
│   ├── C1. 浏览器 DevTools Protocol (CDP)
│   ├── C2. 系统代理抓包
│   └── C3. VPN/TUN 级抓包
│
├── D. Cookie/Session 复用
│   ├── D1. 手动导入 Cookie
│   ├── D2. 扫码后自动提取
│   └── D3. 多账号 Session 池
│
└── E. 手动录入（兜底方案）
    ├── E1. 粘贴支付链接
    ├── E2. 上传二维码图片
    └── E3. 输入卡密
```

### 2.2 各手段详细设计

---

#### A. 浏览器自动化（PC 端）

**适用场景：** 第三方平台有 Web 版支付页面

**A1. 全自动模式**

```
条件：已有有效的 Cookie/Session

流程：
1. 工具启动 Playwright 无头浏览器
2. 注入 Cookie → 自动登录
3. 导航到充值卡/礼品卡购买页
4. 选择面额 + 数量
5. 进入支付页面
6. 捕获支付二维码/支付链接
7. 保存到本地 → 上传平台
8. 关闭浏览器实例

优势：完全无人值守，适合批量操作
局限：部分平台有反自动化检测（webdriver 特征）
```

**A2. 半自动模式（需人工介入）**

```
条件：需要扫码登录 / 图形验证码 / 短信验证

流程：
1. 工具打开浏览器窗口（非无头，用户可见）
2. 弹出登录二维码 → 用户用手机扫码
3. 工具自动检测登录成功（监听 URL 变化 / Cookie 变化）
4. 登录后自动进入购买页
5. 用户选择面额数量（或工具预设）
6. 工具自动捕获支付链接
7. 用户如需支付则弹出支付二维码（在手机上完成）
8. 工具持续监听支付结果
9. 支付成功后，工具抓取卡密/跳转链接

交互要点：
- 浏览器窗口显示在工具界面中（内嵌 WebView）或单独弹出
- 工具界面显示当前步骤提示
- 用户只需要做"扫码"和"支付"两步
```

**A3. 手动辅助模式（元素标记）**

```
条件：平台页面结构复杂，自动化脚本难以覆盖

流程：
1. 工具打开目标平台页面
2. 用户手动登录、导航到支付页面
3. 用户点击工具上的"捕获"按钮
4. 工具通过 CDP 协议获取当前页面的：
   └─ 页面 URL
   └─ 网络请求中的支付链接
   └─ 页面中的二维码图片
   └─ 剪贴板内容
5. 用户确认后保存

优势：几乎覆盖所有平台，不需要写适配器
局限：需要用户手动操作
```

**B1. 自动代理抓包（推荐方案）**

```
流程：
1. 工具自动启动 Android 模拟器（预设镜像）
2. 模拟器中已预装目标平台 App
3. 设置系统代理到本地 mitmproxy
4. 安装 mitmproxy CA 证书到模拟器（自动）
5. 工具通过 ADB 命令操作 App：
   ├─ adb shell am start -n com.xxx/.MainActivity
   ├─ 自动登录（或等待用户扫码）
   └─ 导航到支付/充值页面
6. mitmproxy 实时捕获网络请求
7. 规则引擎过滤出支付相关的请求：
   ├─ 支付链接（alipay:// / weixin://）
   ├─ 订单创建响应
   └─ 二维码图片内容（base64）
8. 提取支付凭证 → 保存到本地
9. 自动切换到下一个账号/任务

关键技术点：
- 模拟器快照：预设登录好的镜像，快速切换账号
- 请求过滤规则：每个平台 App 有不同的支付 URL 特征
- HTTPS 解密：mitmproxy 透明代理 + 证书注入
```

**B2. App WebView 注入**

```
原理：
  部分 App 的支付页面使用 WebView 加载
  工具通过 ADB + Chrome DevTools Protocol 连接到 App 的 WebView
  直接注入 JavaScript 提取支付信息

流程：
1. App 打开支付 WebView
2. 工具检测到 WebView 可用（通过 adb forward tcp:9222）
3. 连接 Chrome DevTools
4. 注入 JS: document.querySelector('img[src*="qrcode"]').src
5. 提取支付二维码/链接
6. 或监听网络请求: performance.getEntriesByType('resource')

优势：不需要代理配置，更隐蔽
局限：仅适用于 WebView 场景
```

**B3. ADB 命令自动化 + 屏幕截图 OCR**

```
流程：
1. 工具通过 ADB 控制模拟器
2. 截图当前屏幕
3. OCR 识别二维码（zbar / pyzbar）
4. OCR 识别文本信息（卡密、订单号）
5. 模拟点击（如需要展开更多信息）
6. 提取凭证

适用场景：
- 支付链接以二维码形式展示
- 卡密以文本形式展示在 App 内
- App 禁止抓包（SSL Pinning）时的兜底方案

局限：速度较慢，需要逐屏分析
```

#### C. 网络请求捕获

**C1. 浏览器 DevTools Protocol (CDP)**

```
非自动化场景，用户已经手动在浏览器中操作

流程：
1. 工具启动 Chrome/Edge 远程调试端口
2. 用户打开一个新标签页，导航到目标平台
3. 用户正常操作（登录、购买、支付）
4. 工具通过 CDP 监听：
   └─ Network.requestWillBeSent
   └─ Network.responseReceived
   └─ Page.downloadProgress（二维码图片下载）
5. 规则引擎过滤支付相关请求
6. 提取支付链接

对比 Playwright 方案：
- 优势：用户自己操作，不会被反爬检测
- 优势：不需要写自动化脚本
- 劣势：需要用户手动完成整个操作流程
```

**C2. 系统级代理抓包**

```
流程：
1. 工具启动本地代理服务器（8080端口）
2. 设置系统代理到 localhost:8080
3. 用户在浏览器中正常访问第三方平台
4. 所有流量经过工具代理
5. 工具从流量中提取支付链接/二维码
6. 支持 HTTPS 解密（需要安装 CA 证书）

优势：系统级捕获，不限于特定浏览器
局限：需要安装系统证书，部分平台有证书锁定
```

---

#### D. Cookie/Session 复用

```
Cookie 是自动化的基础资源。

管理能力：
├── 手动导入：用户从浏览器导出 Cookie → 粘贴到工具
├── 自动提取：扫码登录后工具自动提取 Cookie
├── 定时检测：每小时检查 Cookie 有效性（发一个简单请求）
├── 自动续期：检测到即将过期，自动尝试刷新
└── 多账号池：同一平台多个账号的 Cookie 轮流使用

Cookie 存储：
- 本地加密存储（AES-256-GCM）
- 每个 Cookie 关联：平台、账号、有效期、最后使用时间
- 敏感操作前检查 Cookie 有效性
```

---

#### E. 手动录入（兜底）

```
最简单的模式，适合临时性或自动化覆盖不了的平台。

录入方式：
├── 粘贴支付链接 → 工具解析 + 标准化 → 保存
├── 上传二维码截图 → 工具识别二维码内容 → 保存
├── 输入卡密 → 验证格式 → 保存
└── 输入订单号 → 工具从平台查询 → 保存
```

## 三、凭证类型与库存模型

### 3.1 凭证类型

| 类型 | 示例 | 有效期 | 获取难度 |
|------|------|--------|---------|
| **支付链接** | `https://pay.jd.com/...` | 通常 30min-2h | 低 |
| **支付二维码（图片/base64）** | 微信/支付宝收款码 | 通常 2-24h | 低 |
| **卡密** | `JD-XXXX-YYYY-ZZZZ` | 固定或按商品 | 中 |
| **直充链接** | `https://recharge.xxx.com/...` | 通常 1-24h | 中高 |
| **Token/Code** | 一次性兑换码 | 一次性 | 高 |

### 3.2 库存生命周期

```
          采集/导入              上传到平台            API支付商下单
       ┌──────────┐           ┌──────────┐           ┌──────────┐
       │  本地待上传 │ ──────→ │ 平台库存池 │ ──────→ │  已消耗   │
       └──────────┘           └──────────┘           └──────────┘
              │                     │
              │                     │ 超时未消耗
              ▼                     ▼
       ┌──────────┐           ┌──────────┐
       │  本地过期  │           │ 平台过期   │
       └──────────┘           └──────────┘
```

### 3.3 库存状态自动管理

```
可用（AVAILABLE）→ 已上传到平台，等待被消耗
已消耗（CONSUMED）→ 已被 API 支付商订单消耗
已过期（EXPIRED） → 超时未被消耗，标记移除
待上传（PENDING） → 已采集但未上传到平台
上传失败（FAILED）→ 上传到平台失败，待重试
```

## 四、与平台交互流程

### 4.1 整体数据流

```
┌──────────────────────────────────────────────────────────────┐
│                        Agent Terminal                         │
│                                                               │
│  ① 采集凭证                                                    │
│  ┌─────────┐ 浏览器自动化 ──→ 支付链接/二维码                   │
│  │ 凭证猎人  │ 模拟器抓包  ──→ 卡密/直充链接                    │
│  │ (采集引擎)│ 手动录入    ──→ 任意凭证                        │
│  └────┬────┘                                                    │
│       │                                                         │
│       ▼                                                         │
│  ② 本地存储                                                    │
│  ┌─────────┐                                                    │
│  │ SQLite   │ ← 凭证暂存，标记状态（待上传/已上传/已消耗/已过期）│
│  └────┬────┘                                                    │
│       │                                                         │
│       ▼                                                         │
│  ③ 上传到平台                                                  │
│  ┌─────────┐                                                    │
│  │ 同步引擎  │ ──→ POST /api/v1/terminal/resources/upload      │
│  └────┬────┘      ← 平台返回 resource_id + 扣除积分             │
│       │                                                         │
│       ▼                                                         │
│  ④ 状态同步                                                    │
│  ┌─────────┐                                                    │
│  │ 状态管理  │ ← 平台通知：凭证已消耗 / 凭证已过期              │
│  └─────────┘   更新本地状态                                     │
└──────────────────────────────────────────────────────────────┘
```

### 4.2 前置条件 — 库存预存机制

这是业务流程中最重要的纠正：

```
API 支付商 发起订单
       │
       ▼
┌──────────────────┐      ┌──────────────────┐
│  平台接收订单请求   │────▶│  检查代理商库存池  │
└──────────────────┘      └────────┬─────────┘
                                   │
                     ┌─────────────┴─────────────┐
                     │                           │
                     有库存                     无库存
                     │                           │
                     ▼                           ▼
              ┌──────────────┐          ┌──────────────┐
              │ 订单创建成功   │          │ 订单创建失败   │
              │ 消耗库存中凭证  │          │ 返回: 库存不足  │
              │ 通知凭证已用   │          │ API支付商无法  │
              │              │          │ 发起此订单    │
              └──────────────┘          └──────────────┘
                     │
                     ▼
              ┌──────────────┐
              │ Agent Terminal│
              │ 收到消耗通知   │
              │ 更新本地状态   │
              │ 触发自动补货   │
              │（如开启）     │
              └──────────────┘
```

### 4.3 与平台的 API 接口

| 接口 | 方向 | 说明 |
|------|------|------|
| `POST /api/v1/terminal/bind` | → | Token 绑定 + 注册终端 |
| `POST /api/v1/terminal/resources/upload` | → | 上传凭证到库存池 |
| `POST /api/v1/terminal/resources/status` | ↕ | 同步凭证状态（已消耗/已过期） |
| `POST /api/v1/terminal/heartbeat` | → | 心跳保活 |
| `WS /api/v1/terminal/notify` | ← | 凭证消耗通知、配置更新 |

## 六、采集任务配置示例

### 6.1 京东支付链接采集（浏览器自动化）

```
场景：代理商需要采集京东E卡的支付链接

方式：浏览器自动化 - 半自动（需扫码登录）

步骤分解：
  1. 工具启动 Playwright 浏览器
  2. 打开 https://card.jd.com/
  3. 检测是否已登录（Cookie 注入）
  4. 未登录 → 弹出二维码 → 用户扫码 → 自动继续
  5. 导航到"京东E卡" → "购买"
  6. 选择面额: 100元 × 1张
  7. 点击"立即购买" → 进入订单确认页
  8. 选择支付方式: 微信支付
  9. 点击"提交订单"
  10. 工具监听 Network 请求:
      └─ 捕获支付链接 (如: weixin://pay/...)
      └─ 或捕获支付二维码 (如: https://qr.weixin.xxx/...)
  11. 验证支付链接可访问（初步）
  12. 保存到本地 SQLite
  13. 上传到平台
  14. 循环 → 下一张（同一浏览器实例继续下单）

每个账号的采集频率限制：
  ├── 同一个账号下单间隔 > 5秒（模拟真人操作）
  ├── 每 30 张后更换账号（降低风控概率）
  └── 每个账号每日上限可配置
```

### 6.2 抖音支付码采集（Android 模拟器抓包）

```
场景：代理商需要采集抖音直播间的支付二维码

方式：模拟器抓包 - 半自动

步骤分解：
  1. 工具启动夜神模拟器（预设镜像）
  2. 启动 mitmproxy（透明代理模式）
  3. 模拟器网络设置为代理模式 → mitmproxy
  4. 启动抖音 App（预装）
  5. 检测登录状态 → 未登录则弹出登录二维码
  6. 用户扫码登录 → 自动继续
  7. 导航到"充值"或"DOU+"页面
  8. 选择充值面额
  9. 进入支付页面
  10. mitmproxy 捕获：
      └─ 请求: pay.douyin.com/create_order
      └─ 响应: {"pay_url": "https://...", "qrcode_url": "..."}
  11. 规则引擎自动提取 pay_url
  12. 验证链接有效性
  13. 保存 → 上传 → 循环

关键技术点：
  ├── mitmproxy 流量过滤规则（只关注支付相关域名）
  ├── SSL Pinning 绕过（如果 App 有证书锁定）
  │   ├── 方案1: 使用 Xposed + JustTrustMe 模块
  │   ├── 方案2: 使用 Frida 脚本 hook SSL 验证函数
  │   └── 方案3: 使用已 root 镜像 + 系统 CA 注入
  └── 模拟器快照管理（多个登录好的镜像快速切换）
```

### 6.3 淘宝直充链接采集（CDP 手动辅助）

```
场景：用户手动操作淘宝下单，工具自动捕获支付信息

方式：CDP 手动辅助

步骤分解：
  1. 工具启动 Chrome 远程调试模式
  2. 在工具界面中嵌入 Chrome 窗口（或用户在新窗口操作）
  3. 用户手动操作：
     └─ 登录淘宝
     └─ 选择充值商品
     └─ 提交订单
  4. 工具通过 CDP 实时监控：
     └─ 当前页面 URL 变化
     └─ Network 请求/响应
     └─ 剪贴板内容（用户可能复制了链接）
  5. 检测到支付链接 → 工具自动捕获
  6. 弹出确认窗口 → 用户确认 → 保存 → 上传
```

### 6.4 多种采集手段组合策略

```
同一个平台的采集策略可以组合使用，提高效率和成功率：

京东采集方案（推荐组合）：
  ├── 主方案: 浏览器自动化（Cookie 有效时全自动）
  ├── 备方案: 浏览器自动化（Cookie 过期时半自动弹窗扫码）
  └── 兜底方案: CDP 手动辅助（页面结构变化时）

抖音采集方案（推荐组合）：
  ├── 主方案: 模拟器抓包（mitmproxy 自动捕获）
  ├── 备方案: ADB 截图 + OCR（App 禁止抓包时）
  └── 兜底方案: 手动录入（用户直接粘贴支付链接）

策略引擎（自动决策）：
  1. 首选 Cookie 有效的全自动模式
  2. Cookie 无效 → 降级为半自动（弹出登录窗口）
  3. 半自动失败 → 尝试模拟器方案
  4. 模拟器不可用 → 降级为 CDP 手动辅助
  5. 以上都不可用 → 提示用户手动录入
```

## 八、与 Super Market 平台的关系

### 8.1 前置依赖

平台侧需要先完成以下功能，终端工具才能正常工作：

| 平台功能 | 说明 | 状态 |
|---------|------|------|
| 库存池 API | 接受凭证上传、返回 resource_id | ✅ 已有（inventory API） |
| 终端绑定 API | Token 生成、终端注册 | 需新增 |
| WebSocket 通知 | 凭证被消耗时通知终端 | 需新增 |
| 积分担保机制 | 上传凭证时锁定代理商的积分作为担保 | 需确认（已有积分冻结逻辑） |

### 8.2 积分担保机制

```
代理商上传支付凭证到库存池时：
  1. 平台按凭证面值冻结代理商等额积分
  2. 凭证被消耗 → 积分正式扣除
  3. 凭证过期 → 解冻积分
  4. 防止代理商上传无效凭证占库存

这个机制确保代理商有动力提供真正可用的凭证。
```
