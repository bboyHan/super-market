# 神谕 (Oracle) — 产品规格定义 v2

> 最终版：2026-06-11

---

## 一、一句话定义

> **开机即用、永远在后台、采集一切数据的隐形采集器。**

用户双击安装后正常用电脑，数据自动出现在面板上。不需要配置、不需要学习、不需要操作。

---

## 二、目标用户 & 使用场景

| 角色 | 关注 | 使用方式 |
|------|------|---------|
| **代理商（主用户）** | 数据到账了吗？每天采集了多少？ | 装完不管，只看 Dashboard |
| **技术运营（次用户）** | 规则覆盖全吗？能加新目标吗？ | 写 JSON 规则，配置新采集目标 |

**设计铁律：所有设计优先服务代理商用户。** 技术运营需要的功能「有就行」，不追求体验。

### 用户操作路径

```
安装：下载 → 双击 → 确认 UAC → 完成（10 秒）
使用：正常用电脑 → 数据自动采集（完全无感）
查看：双击托盘图标 → 浏览器打开 Dashboard
配置：Dashboard 上开关模式、查看状态（可选）
卸载：控制面板卸载（自动清理驱动和证书）
```

### 技术选型依据

```
为什么是 Windows Service 而不是 Console？
  → 用户不需要看到控制台窗口
  → 开机自启不需要用户登录
  → 崩溃自动恢复
  → 不占任务栏

为什么是 ASP.NET Core 内嵌页面而不是前后端分离？
  → Dashboard 不需要复杂交互（表格 + 表单 + 图表）
  → 无 node_modules，无构建流程
  → 部署就是一个 exe，零依赖

什么是「内嵌 SPA」？
  → wwwroot/index.html + app.js + style.css
  → ASP.NET Core app.UseStaticFiles() 直接托管
  → 所有 API 调用走 fetch('/status') 相对路径
```

## 四、安装体验（最关键的 10 秒）

```
用户下载 Oracle_Setup.exe（~15MB）

双击 → 安装向导
  ┌────────────────────────────────────────────┐
  │  神谕 数据采集引擎 v1.0                     │
  │                                            │
  │  安装目录: C:\Oracle\                      │
  │  ☑ 开机自启                                │
  │  ☑ 采集模式: 标准（DNS 劫持 + HTTPS 解密） │
  │                                            │
  │           [ 安装 ]                         │
  └────────────────────────────────────────────┘

用户点击 [安装] → UAC 确认（只有这一次）

安装程序自动完成：
  1. 解压文件到 C:\Oracle\
  2. 注册 Windows 服务
  3. 安装 WinDivert 驱动（如需要）
  4. 生成根 CA 证书 + 导入系统受信任存储
  5. 启动服务
  6. 创建桌面快捷方式
  7. 打开浏览器 → Dashboard

完成。整个过程用户只需要点两次鼠标：[安装] + [确认 UAC]
```

## 六、核心架构：可插拔采集通道

### 6.1 架构总览

```
┌──────────┐  ┌──────────┐  ┌──────────┐  ┌──────────┐
│ 数据来源  │  │ 采集通道   │  │ 协议解析   │  │ 规则提取   │  → 输出
│          │  │ (Channel) │  │ (Parser) │  │ (Rule)   │
├──────────┤  ├──────────┤  ├──────────┤  ├──────────┤
│ 浏览器    │→│ CDP      │→│ HTTP     │→│ 正则     │→ Dashboard
│ PC QQ     │→│ WinDivert│→│ HTTPS    │→│ JSONPath │→ Python后端
│ 端游      │→│ 进程注入  │→│ WebSocket│→│ 脚本     │→ Webhook
│ 手游模拟器 │→│ TUN      │→│ 自定义协议 │→│          │→ 文件导出
│ 手机热点   │→│ WFP      │→│          │  │          │
└──────────┘  └──────────┘  └──────────┘  └──────────┘
```

### 6.2 Channel 接口定义

```csharp
/// 每种采集方式实现一个 Channel
public interface ICaptureChannel
{
    string Name { get; }                    // "WinDivert", "ProcessInject"...
    string Description { get; }             // 人类可读的描述
    ChannelCapability Capability { get; }

    Task<bool> InitializeAsync();           // 初始化
    Task StartAsync();                      // 开始采集
    Task StopAsync();                       // 停止采集
    bool IsHealthy { get; }                 // 健康检查

    event Action<RawPacket> OnPacket;       // 原始数据 → 通知协议层
}
```

### 6.3 Channel 全景与阶段

```
Channel           状态    覆盖范围          管理员  TLS解密  计划阶段
────────────────────────────────────────────────────────────────────
WinDivert         ✅ 已有 PC 全流量         ✅     ❌      Phase 1
DnsSpoof          ✅ 已有 PC DNS 劫持       ✅     ❌      Phase 1
TlsProxy(MITM)    ✅ 已有 PC HTTPS 解密     ✅     ✅      Phase 1
ProcessInject     🔧 规划 PC 端游/应用      ✅     ✅      Phase 3
AndroidEmulator   🔧 规划 手游(模拟器)      ❌     ✅      Phase 3
BrowserCDP        🔧 规划 浏览器             ❌     ❌     Phase 2
WFP QUIC Block    🔧 规划 QUIC 降级 TCP     ✅     ❌      Phase 2
TUN               📋 远期 手机热点          ✅     ❌      Phase 4
```

## 九、不做什么（明确边界）

```
明确不做：
  ❌ 不篡改任何请求/响应内容（只读采集）
  ❌ 不拦截非目标流量（只处理支付域名）
  ❌ 不做全流量记录（只存提取的结构化数据）
  ❌ 不做用户账户系统（纯本地单用户）
  ❌ 不依赖第三方云服务（纯本地运行）
  ❌ 不用 Electron（太重、内存占用大）
  ❌ 不用 Python（性能、打包体积、部署复杂度）

为什么不用 Python？
  Phase 1 很多方案选 C# 而非 Python 的原因：
    - Windows Service 原生支持 (.NET)
    - SChannel 只能从 .NET/C++ 调用
    - 单文件发布（self-contained）
    - 性能：包处理场景 C# 比 Python 快 10-50x
    - 内存：~30MB vs Python ~100MB+
  
  Python 的定位：
    - 作为后端数据接收方（已有 server/app/）
    - 不作为核心引擎
```
