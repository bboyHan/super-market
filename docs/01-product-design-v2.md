# VBox — B2B2B 虚拟数字资产分销与API交易平台（产品设计说明 V2.1）

> V2.1 修正：供应商可充值划转积分给代理商、平台管理员统管货品品类授权、订单确认分自动/手动两种模式、新增对账看板

## 一、产品概述

### 1.1 一句话定义

> **一个以"积分"为唯一内部结算媒介，让虚拟货品供应商通过代理商网络实现自动化分销和API交易交付的管理平台。**

### 1.2 核心模式拆解

```
    ┌──────────────── 线下资金流 ────────────────┐
    │                                             │
    │  API 支付商 ──── 人民币/USDT ────▶ 供应商   │
    │       ↑ 平台不介入资金，只管理业务           │
    └────────────────────────────────────────────┘
                       ↑
    ┌──────────────── 平台内操作流 ───────────────┐
    │                                             │
    │  USDT ──1:1──▶ 积分 (供应商+代理商)         │
    │                     │                       │
    │             供应商积分账户                    │
    │               │         │                   │
    │         划转给代理商  支付平台费用            │
    │               │                             │
    │             代理商积分账户                    │
    │               │                             │
    │  供应商      代理商            API支付商     │
    │  (后台UI)    (后台UI)          (纯API)      │
    │  │            │                 │          │
    │  ├─充值积分   ├─接收供应商划转   ├─API下单  │
    │  ├─划转代理商 ├─上传库存        ├─查订单   │
    │  ├─确认收款   ├─自动交付        ├─收回调  │
    │  ├─纳管API商  └─积分消耗         │          │
    │  ├─看对账看板                    └──────────│
    │  └─品类日结统计                              │
    │                                              │
    │  积分流向：USDT→积分→供应商→代理商→消耗     │
    │             (代理商也可自行充值)              │
    └──────────────────────────────────────────────⎦
```

### 1.3 重要边界

| 边界 | 说明 |
|------|------|
| **积分不可提现** | USDT → 积分是单向通道，任何人不可逆向操作 |
| **积分可划转** | 供应商可将自身积分划转给代理商（单向），代理商无划转权限 |
| **积分≠真实财富** | 积分是平台内的「预抵扣额度计量单位」，不是可兑现的资产 |
| **线下资金流** | API 支付商与供应商之间的真实资金结算发生在线下，平台不介入 |
| **API支付商不进入平台** | API 支付商仅调用 API，看不到平台UI，由供应商在后台纳管 |
| **货品由平台创建** | 货品品类由平台管理员统一创建，授权给供应商使用 |

## 三、积分体系详解

### 3.1 积分本质

积分是平台内部的 **预抵扣额度计量单位**，本质上是 **API 支付商的信用预授权**。

| 核心概念 | 说明 |
|---------|------|
| 积分 = 预抵扣额度 | 代理商充值 USDT 获得的积分，用于"担保"其能完成 API 支付商的订单交付 |
| 资金来源 | 供应商充值 + 代理商自充值，供应商可将积分划转给代理商 |
| 工作原理 | API 支付商下单 → 订单支付确认 → 平台扣除代理商积分 → 代理商交付 |
| 积分消耗 | 代理商被扣减的积分，代表其"预抵扣额度"已使用，需要供应商划转或自行充值 |
| 积分≠收入 | 积分不是"赚到的钱"，而是"已使用掉的信用额度" |

### 3.2 积分流向全景

```
                USDT（链上）
                    │
                    │ 1:1 实时汇率（供应商+代理商均可充值）
                    ▼
            积分（平台内 — 预抵扣额度）
                    │
         ┌──────────┴──────────┐
         │                     │
   供应商积分账户        代理商积分账户(自充值)
         │                     │
         │  可划转给代理商       │
         │  (单向不可逆)         │
         └──────▶ 代理商积分账户(接收)
                       │
                  ┌────┴────┐
                  │         │
              可用余额   已冻结余额
                  │         │
                  │    API 订单发生时：
                  │    ① API支付商下单
                  │    ② 订单支付确认(自动/手动)
                  │    ③ 冻结 → 扣除
                  │         │
                  └─────────┘
                       │
                       ▼
          代理商积分减少 = 预抵扣额度已使用
          供应商可再划转 / 代理商自行充值
```

### 3.3 交易时的积分转移

```
API 支付商下单（单价 100 积分，数量 1）
                     │
                     ▼
          ┌─────────────────────┐
          │  平台收到订单请求    │
          └──────────┬──────────┘
                     │
          ┌──────────▼──────────┐
          │  路由到可用代理商   │
          │  代理商积分：1000   │
          │  本次需冻结：100    │
          └──────────┬──────────┘
                     │
          ┌──────────▼──────────┐
          │  订单创建成功        │
          │  status=PENDING     │
          │  100 积分已冻结      │
          └──────────┬──────────┘
                     │
          ┌──────────▼──────────┐
          │  订单支付确认        │
          │  (自动或手动模式)    │
          └──────────┬──────────┘
                     │
          ┌──────────▼──────────┐
          │  积分正式扣减：      │
          │  代理商：-100       │
          │  （预抵扣额度使用）  │
          │  冻结→已扣除       │
          └──────────┬──────────┘
                     │
          ┌──────────▼──────────┐
          │  代理商完成交付      │
          │  回调通知 API支付商  │
          └─────────────────────┘

      代理商积分从 1000→900
      可用额度减少 100
      供应商可再划转或代理商自行充值
```

### 3.4 为什么积分不可提现？

因为积分不是"赚到的钱"，而是 **"已充值待消耗的预抵扣额度"**：

1. **代理商充值 USDT → 积分**：不是为了投资，而是为了获得"售卖资格"——证明自己有履约能力
2. **供应商充值 USDT → 积分**：用于划转给代理商，管理自己的分销网络
3. **交易发生时**：积分被消耗，代表售卖资格已使用
4. **如果积分可提现**：代理商可以先充值 → 获得售卖资格 → 卖完后提现 → 等于空手套白狼

## 四、完整交易流程

### 4.1 流程全景

```
┌─────────────────────────────────────────────────────────────────┐
│                    事前准备（线上）                              │
├─────────────────────────────────────────────────────────────────┤
│                                                                  │
│  ① 平台管理员创建货品品类，授权给供应商                         │
│  ② 供应商注册 → 获得授权货品列表                                │
│  ③ 供应商创建代理商 → 授权货品 → 划转积分或代理商自充值        │
│  ④ 代理商上传货品库存（卡密/Token）                             │
│  ⑤ 供应商在线下对接 API 支付商 → 在平台创建 API 支付商账号     │
│                                                                  │
├─────────────────────────────────────────────────────────────────┤
│                    交易执行（线上自动或手动确认）                │
├─────────────────────────────────────────────────────────────────┤
│                                                                  │
│  ⑥ API 支付商调用 POST /order/create                           │
│  ⑦ 平台校验 → 路由到有库存的代理商 → 冻结积分                   │
│  ⑧ ┌ 自动模式：系统通过外部渠道验证支付 → 自动继续              │
│     └ 手动模式：供应商/代理商登录后台确认收款 → 继续             │
│  ⑨ 扣除代理商积分 → 代理商交付货品                              │
│  ⑩ 回调通知 API 支付商                                          │
│                                                                  │
├─────────────────────────────────────────────────────────────────┤
│                    事后管理（线上）                              │
├─────────────────────────────────────────────────────────────────┤
│                                                                  │
│  ⑪ 供应商查看对账看板（按 API支付商 / 按品类 的日结统计）      │
│  ⑫ 代理商查看交易记录和结算报表                                 │
│  ⑬ 平台管理员监控系统、处理异常                                 │
│                                                                  │
└─────────────────────────────────────────────────────────────────┘
```

### 4.2 下单交付时序图（自动模式 vs 手动模式）

根据货品类型，订单支付确认分为两种模式：

```
┌──────────────────────────────────────────────────────────────────┐
│  模式A：自动确认（系统自动查询验证）                              │
│  API支付商下单 → 平台通过外部渠道验证支付 → 自动回调             │
│  适用于：系统可以自动查询支付状态的货品                          │
└──────────────────────────────────────────────────────────────────┘

┌──────────────────────────────────────────────────────────────────┐
│  模式B：手动确认（供应商/代理商人工确认）                        │
│  API支付商下单 → 供应商/代理商登录后台确认收款 → 发起回调       │
│  适用于：系统无法自动确定支付状态的货品                          │
└──────────────────────────────────────────────────────────────────┘
```

### 4.3 订单支付确认详解

```
┌─────────────────────────────────────────────────────────────┐
│           关键步骤：订单支付确认                              │
├─────────────────────────────────────────────────────────────┤
│                                                              │
│  【自动模式】                                                 │
│  ① API支付商下单 → 订单进入自动验证流程                       │
│  ② 平台通过预先配置的外部渠道查询支付状态                      │
│  ③ 验证通过 → 自动继续（扣除积分→交付→回调）                 │
│  ④ 验证失败 → 降级为手动模式或标记异常                       │
│                                                              │
│  【手动模式】                                                 │
│  ① API支付商下单 → 订单状态 = PENDING（待确认）               │
│  ② API支付商线下向供应商付款                                  │
│  ③ 供应商登录后台 → 待确认订单列表 → 点击"确认收款"           │
│  ④ 平台冻结代理商积分 → 扣除 → 下发交付指令                   │
│  ⑤ 代理商交付完成 → 平台回调通知 API 支付商                   │
│                                                              │
│  超时处理：超过 N 分钟未确认 → 自动取消并释放冻结积分          │
│                                                              │
└─────────────────────────────────────────────────────────────┘
```

### 4.4 订单路由策略（供应商控制的分配规则）

当 API 支付商下单时，平台需要从多个代理商中选择谁来提供货品。供应商可以为**每个货品**独立配置路由策略。

```
┌─────────────────────────────────────────────────────────────────┐
│                        订单路由引擎                              │
├─────────────────────────────────────────────────────────────────┤
│                                                                  │
│  收到订单请求 → 确定货品ID → 查询可用代理商列表                  │
│       │                                                         │
│       ▼                                                         │
│  ┌─────────────────────────────────────────────────────┐       │
│  │  策略1：轮询（Round-Robin）— 默认                    │       │
│  │  所有提供该货品的代理商按顺序轮流接单                 │       │
│  │  A → B → C → A → B → C ...                         │       │
│  │  适用：各代理商均衡分配，无优先级差异                 │       │
│  └─────────────────────────────────────────────────────┘       │
│                                                                  │
│  ┌─────────────────────────────────────────────────────┐       │
│  │  策略2：优先（Priority）                            │       │
│  │  指定代理商A优先提供 → A库存耗尽 → 切换到B         │       │
│  │  A → A → A ... A(耗尽) → B → B ...                │       │
│  │  适用：核心代理商优先消化，或集中清库存              │       │
│  └─────────────────────────────────────────────────────┘       │
│                                                                  │
│  ┌─────────────────────────────────────────────────────┐       │
│  │  策略3：权重（Weighted）                            │       │
│  │  按比例分配：A:70%, B:30%                          │       │
│  │  每10单中，A接7单，B接3单                          │       │
│  │  适用：精细控制各代理商的订单量占比                 │       │
│  └─────────────────────────────────────────────────────┘       │
│                                                                  │
│  供应商可随时关停/启用某代理商的提供权                           │
│  （如代理商A库存不足时临时关闭，全部流量切到B）                 │
│  配置保存后即时生效                                            │
│                                                                  │
└─────────────────────────────────────────────────────────────────┘
```

对接文档 URL:    https://docs.vbox.com/api

API 支付商通过以下方式完成工作：

```
① 获取产品列表（查看供应商授权给自己的货品和价格）

④ 接收交付内容（卡密/Token 在回调中返回）
⑤ 线下与供应商结算（通过双方约定的方式）
```

## 六、开放 API 规范（面向 API 支付商）

### 6.1 接口清单

| 接口 | 方法 | 用途 | 是否需要签名 |
|------|------|------|-------------|
| `/v1/products` | GET | 获取可购货品列表 | 是 |
| `/v1/order/create` | POST | 创建采购订单 | 是 |
| `/v1/order/query` | POST | 查询订单状态 | 是 |
| `/v1/order/detail` | GET | 获取订单详情（含交付内容） | 是 |

### 6.2 订单状态机

```
SUBMITTED ──▶ PENDING ──▶ DELIVERING ──▶ SUCCESS
  (已提交)     (待确认)    (交付中)       (已完成)
        │          │           │
        ▼          ▼           ▼
     CANCELLED   EXPIRED     FAILED
    (已取消)    (已超时)    (交付失败)
```

> PENDING 状态：自动模式的订单等待系统验证，手动模式的订单等待供应商/代理商确认
> 自动验证失败可降级为手动模式

### 6.3 请求规范

```
POST https://api.vbox.com/v1/order/create

Headers:
  Content-Type: application/json
  X-API-Key: sk_liv...xxxx
  X-Timestamp: 1704067200
  X-Signature: HMAC-SHA256(api_secret, sorted_params + body + timestamp)

Body:
{
  "product_id": "jd_e100",
  "quantity": 1,
  "client_order_id": "ORD-20250101-001",
  "callback_url": "https://merchant.example.com/callback"
}

Response:
{
  "code": 0,
  "message": "success",
  "data": {
    "platform_order_id": "PO2025010100001",
    "client_order_id": "ORD-20250101-001",
    "status": "PENDING",
    "created_at": "2025-01-01T12:00:00Z"
  }
}
```

### 6.4 回调通知

```
POST {callback_url}

Body:
{
  "platform_order_id": "PO2025010100001",
  "client_order_id": "ORD-20250101-001",
  "status": "SUCCESS",
  "deliveries": [
    {
      "type": "card_key",
      "content": "JD-XXXX-YYYY-ZZZZ",
      "delivered_at": "2025-01-01T12:00:05Z"
    }
  ],
  "timestamp": 1704067205,
  "signature": "HMAC-SHA256(api_secret, sorted_body)"
}
```

### 6.5 错误码

| Code | 含义 | 说明 |
|------|------|------|
| 0 | 成功 | 请求处理成功 |
| 40001 | 签名错误 | X-Signature 校验失败 |
| 40002 | 时间戳过期 | 与服务器时间差超过 300 秒 |
| 40003 | IP 不在白名单 | 请求 IP 未被授权 |
| 40301 | 无权限 | 无该货品的访问权限 |
| 40401 | 货品不存在 | product_id 无效 |
| 50001 | 库存不足 | 所有代理商库存均不足 |
| 50002 | 交付超时 | 代理商未在有效时间内完成交付 |

### 7.3 高频交易注意

```
积分交易属于高频场景，需考虑：

1. 数据写入：日订单量可能 10万+，MySQL 单表压力大
   → 方案：分表（按天/月）或时序数据库

2. 实时统计：今日数据需秒级更新
   → 方案：Redis 计数 + 定时落盘

3. 对账查询：昨日/前日数据快速加载
   → 方案：预聚合表（每小时/每天聚合一次）

4. 报表导出：CSV/Excel 导出不能拖慢主库
   → 方案：从库/只读副本
```

## 八、货品与库存模型

### 8.1 货品模型

```
Product（货品品类 — 由平台管理员创建）
├── id
├── name: 货品名称（如"京东E卡 100元面额"）
├── category: 分类（游戏点卡/电商卡券/会员权益/账号/Token...）
├── face_value: 面值（积分）
├── suggested_price: 建议售价（积分）
├── description: 货品描述
├── delivery_mode: 交付模式（AUTO_CARD_KEY / AUTO_TOKEN / MANUAL）
├── confirm_mode: 确认模式（AUTO / MANUAL）
├── status: 上架/下架
└── created_at / updated_at

SupplierProductAuthorization（供应商授权）
├── id
├── supplier_id: 供应商
├── product_id: 货品
├── settlement_price: 结算价（供应商从代理商处的结算价）
├── status: 生效/失效
└── created_at

AgentAuthorization（代理商授权）
├── id
├── supplier_id: 供应商
├── agent_id: 代理商
├── product_id: 货品
├── agent_price: 代理商售价
├── status: 生效/失效
└── created_at

InventoryItem（库存单元 — 代理商持有）
├── id
├── agent_id: 所属代理商
├── product_id: 所属货品
├── content: 交付内容（加密存储）
├── status: 可用/已售/已过期
├── order_id: 绑定订单
└── expires_at: 过期时间（可选）
```
